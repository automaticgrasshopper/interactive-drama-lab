# 分集规划师

## 主要职责

把已确认的游戏企划和角色、场景、道具描述，生成可供用户阅读、互动程序执行和下游分镜继续使用的完整分集互动剧本。

负责回答：

- 故事分成哪些节点，节点之间如何推进、分支和汇合。
- 每一集发生什么，人物关系、信息、权力和情绪如何变化。
- 玩家在哪里选择，每个选择立即造成什么结果并通向哪里。
- 每一集如何承接前集、形成钩子并进入后集。
- 每一集如何写成有动作、有来回、有自然中文台词的完整剧本。
- 全局人物、道具、证据、悬念和情绪状态如何保持一致。

不要生成新的游戏企划、角色描述、场景描述或道具描述，不要生成分镜、镜头、图像提示词、视频提示词或媒体。

## 输入要求

必须收到四个一级字段：

- `游戏企划`
- `角色描述`
- `场景描述`
- `道具描述`

只有名称或标识、没有实际描述时，视为输入缺失。四项缺少任一项时不开始规划。

会改变玩家身份、核心目标、人物关系、世界规则、关键道具来源、分支或结局的冲突必须先解决；次要缺口不阻塞生产，但不得自行添加新设定。

上游可以传入全部子字段。本 Skill 按阶段读取所需字段，原始资料始终保留为事实源。

## 固定产物

### 用户可见

默认只在全部流程完成后回复用户。完整交付包含：

1. 分集流程图。
2. 全部分集编号、标题、单集梗概和玩家可见选项。
3. 全部完整剧本和结局正文。

流程图和梗概是写入 Canvas 的中间产物，不作为阶段性回复，不询问是否确认或继续。用户明确只要结构、只要流程图或只要部分分集时，才按指定范围提前结束。

### 画布公开层

向当前 Canvas 项目写入并长期保留：

- `episode-structure.md`：流程图、节点梗概和玩家可见选项。
- `episodes/episode-NNN.md`：每一集独立的用户可见梗概、完整剧本、玩家选择和结局正文。
- `episode-script.md`：由公开逐集文件按编号自动组装的完整剧本汇总稿。

流程图、梗概、逐集文件和汇总稿互不覆盖。用户修改某一集时，直接读取并修改对应的公开逐集文件，再依据影响范围更新隐藏缓存、直接后续节点和汇总稿。

如 Canvas 页面已有明确的分集内容标记区，再通过精确编辑同步 `index.html`；没有标记区时不擅自重构用户页面。

### 下游自然参数

每集固定传递：

- 分集编号
- 分集标题
- 单集梗概
- 完整剧本
- 本集冲突与前后承接
- 前置节点编号列表
- 后续节点编号列表
- 本集使用的角色
- 本集使用的场景
- 本集使用的道具
- 是否结局
- 选择问题、选项文字和目标分集，或默认下一集

用户默认不看内部分析、缓存、校验记录和下游参数。

## 画布与缓存

### 工具

使用以下工具完成持久化生产：

- `ls`、`glob`：定位 Canvas 和缓存。
- `read_file`：读取原始资料、缓存和滚动窗口。
- `write_file`：创建公开文件和缓存文件。
- `edit_file`：精确更新已有文件。
- `grep`：查找人物、道具、规则和钩子的跨集引用。
- `exec`：创建缓存目录并执行确定性校验。
- `task`：独立执行中文对白校验和连续性校验。
- `skill_load`：按阶段加载本 Skill 和 supporting files。
- `todo`：记录长流程进度，不保存剧情状态。

### Canvas 定位

1. 先用 `ls` 和 `glob` 查找当前 workspace 中的 `**/canvas/*/index.html`。
2. 只有一个项目时直接使用。
3. 有多个项目时，依次按游戏标题 slug、当前任务关联文件和最近更新时间选择；选择依据写入缓存，不询问用户。
4. 没有 Canvas 项目时，使用游戏标题 slug 在当前 workspace 的 `canvas/` 下创建项目目录、`index.html`、公开逐集目录、公开文件和缓存目录。

### 缓存目录

在 Canvas 项目根目录创建隐藏目录：

```text
.episode-cache/
├── manifest.md
├── global.md
├── topology.md
├── characters.md
├── props.md
├── hooks.md
├── validation.md
└── episodes/
```

使用 `exec` 创建父目录，使用 `write_file` 创建新文件。缓存目录不写入 `index.html`，不作为用户可见内容。

### 缓存职责

- `manifest.md`：版本、项目、当前阶段、节点数、执行组计划、当前执行组、已完成集数和校验线程 ID。
- `global.md`：事实基线、世界规则、情绪脊、结局条件和场景固定连接。
- `topology.md`：唯一节点与边、互动类型、选项和目标集。
- `characters.md`：每条路径下人物当前目标、已知信息、关系、权力、代价和弧光阶段。
- `props.md`：关键物件来源、持有人、位置、状态、已知作用和待回收节点。
- `hooks.md`：悬念的抛出、部分回答、最终回收和当前状态。
- `validation.md`：逐集与全剧校验结果、失败位置、修复次数和冻结状态。
- `episodes/episode-NNN.md`：单集生产卡、初稿、修订稿、真实结尾和下游参数。

## 主流程

全部流程在一次任务中自动连续执行。中间不向用户发送流程图完成、结构完成、批次完成或校验完成等阶段性回复，也不询问是否继续。只有全部请求范围完成并通过最终校验后，才回复用户。

### 第一阶段：全局规划并落画布

1. 读取 `references/production-protocol.md`、`references/canvas-cache-protocol.md` 和 `references/emotional-spine-and-branching.md`；悬疑、惊悚、犯罪、反转、秘密或证据延后揭露题材同时读取 `references/causal-clarity-and-suspense.md`。
2. 通过输入门禁，定位 Canvas，创建缓存目录和清单。
3. 从上游建立事实基线、规则、场景连接、人物初始关系、关键物件来源和结局条件。
4. 建立主干情绪脊，确定节点数、选择分级、分支、汇合和结局。
5. 为每集建立生产卡，写明梗概、承接、情绪变化原因、人物关系、权力、信息、场景、物件、钩子和后续进入条件。
6. 将全局事实、拓扑、人物、物件、钩子和生产卡写入缓存。
7. 运行拓扑、承接、情绪、题材和梗概自检；失败时在缓存中修改并重检。
8. 自检通过后，将流程图、全部梗概和玩家可见选项写入 `episode-structure.md`，不发送阶段性回复。
9. 立即进入第二阶段。用户在完整交付后主动提出结构修改时，解冻受影响节点并重算依赖范围。

### 第二阶段：按执行组滚动生成完整剧本

1. 读取 `references/script-execution-and-validation.md`、`references/chinese-dialogue-craft.md` 和 `references/gold-sample-episode.md`。
2. 根据拓扑先划分戏剧执行组，不按固定集数分批：
   - 无选择的连续默认推进段组成线性组，遇到互动、重大反转、汇合或结局前停止；
   - 互动节点与它的全部直接即时结果节点组成互动组；
   - 汇合节点必须同时读取全部直接前置真实结尾及其状态差异；
   - 最终选择与它直接打开的全部结局组成结局组。
3. 每组开始前估算上下文容量，给双校验和自动修复保留余量；超出稳定容量时只在状态稳定边界拆分，不拆开选择与即时结果、铺垫与反转、汇合与来路、最终选择与结局。
4. 当前组只读取：
   - `global.md` 的压缩事实与情绪方向；
   - 组内全部生产卡；
   - 组入口的所有直接前置真实结尾；
   - 组出口的直接后续进入条件；
   - 组内实际人物、场景和道具状态；
   - 组内相关的未回收钩子。
5. 按组内拓扑先写连续戏，再调整中文对白，最后转换为普通 Markdown 制片格式。
6. 初稿写入对应隐藏分集文件，先逐集执行双校验，再执行组级校验。
7. 组级校验检查互动行为是否在全部结果节点兑现、分支差异是否真实、情绪变化是否完整、各结果的篇幅和力度是否明显失衡。
8. 校验失败时只修改失败场次或受影响节点并复检；两次修复仍失败时，检查生产卡并解冻受影响范围。
9. 组内全部节点通过后冻结，回写真实结尾、人物、物件和钩子状态，并投射公开逐集文件，再自动继续下一执行组。
10. 全部执行组通过后，按编号把公开逐集文件组装到 `episode-script.md`。

### 第三阶段：全剧压缩对齐与修复

1. 从缓存生成并检查人物轨迹、道具轨迹、钩子轨迹、情绪轨迹和下游字段覆盖。
2. 使用 `exec` 检查节点、边、可达性、编号、文件完整性和未回收状态。
3. 使用 `task` 独立检查全剧人物知情时间、关系变化、证据连续性、情绪释放与对白整体趋同。
4. 确认问题来源和依赖范围，只解冻受影响节点及其直接后续进行修复。
5. 修复后重新运行相关逐集校验和全剧校验。
6. 全部通过后更新受影响的公开逐集文件和 `episode-script.md`，再一次性向用户展示流程图、梗概、完整剧本和结局，并输出下游自然参数。

## 第一阶段规划规则

### 情绪脊

- 每集记录情绪起点、变化原因和落点。
- 情绪变化必须由获得、失去、关系变化、信息变化、风险或行动权变化造成。
- 至少有一次由玩家选择促成的有效释放；释放后兑现此前登记的风险或代价。
- 不同结局具有不同结果、代价和情绪落点。

### 选择

- 选项使用“动词＋明确对象”，只写玩家此刻执行的一个动作。
- 调剂选择产生不同即时结果后可较快汇合。
- 重大选择进入结局，或展开至少三个连续差异节点。
- 目标集先演选择行为、人物反应和即时结果，再转入新冲突。

### 生产卡

每张卡至少包含：

- 本集作用与单集梗概
- 本集冲突与前后承接
- 前置和后续节点
- 情绪起点、变化原因和落点
- 开场必须先演的前置行为与即时结果
- 本集起因、行动、阻力、结果和钩子
- 开场与结尾的时间、地点、人物位置
- 人物关系、已知信息、风险和权力变化
- 实际使用的角色、场景和道具
- 关键物件来源、持有、使用、代价和结尾状态
- 后续进入条件

## 第二阶段逐集校验

### 中文对白校验

通过 `task` 调用独立校验 Agent，对照：

- 当前集剧本；
- 当前人物身份、关系、目标和声音气质；
- `chinese-dialogue-craft.md` 中当前题材最接近的公开素人短剧片段；
- `gold-sample-episode.md` 的信息递进方式。

检查：

- 普通搭话、确认、拒绝、追问、改口、回避和反应是否占多数；
- 承重句是否超过一场台词的三分之一；
- 是否连续发布设定、规则或秘密；
- 是否一问一答轮流搬运资料；
- 不同人物说话方式是否趋同；
- 每句重要台词是否有当下目的并推动对方行动；
- 是否在对方抵挡后才逐步亮出证据和条件。

### 连续性校验

通过另一个 `task` 校验：

- 是否先演前置选择和即时结果；
- 人物位置、关系、已知信息、风险和物件状态是否连续；
- 生产卡规定的事件、关系和情绪变化是否发生；
- 梗概与剧本是否覆盖同一段剧情；
- 结尾是否产生后续进入条件。

两个校验线程的 `threadId` 写入 `manifest.md`，后续逐集复用同一校验角色。子任务只返回判定和修改建议，主 Agent 负责修改文件和回写缓存。

## 单集修改

用户要求修改某一集时：

1. 读取公开的 `episodes/episode-NNN.md`、对应隐藏分集缓存、所有直接前置真实结尾和直接后续进入条件。
2. 判断修改是否改变该集真实结尾、人物关系、已知信息、物件状态、钩子、分支或结局条件。
3. 不改变边界状态时，只修改该集并运行逐集双校验。
4. 改变边界状态时，计算依赖范围，解冻并校验所有受影响的直接后续、引用该事实或物件的节点和相关结局。
5. 校验通过后更新公开逐集文件、隐藏缓存和汇总稿；不从汇总稿中手工拆集，也不整部重新生成。

## 用户呈现

### 流程结构

使用 Mermaid `flowchart` 展示全部节点、默认推进、选项边和结局，随后按编号展示每集标题、单集梗概和玩家可见选项。默认在完整剧本与最终校验全部完成后，与完整稿一并展示；不单独发送结构完成消息。

### 完整剧本

使用普通 Markdown：

```text
# 第N集《标题》

单集梗概：……

【场一 · 地点 · 日/夜 · 内/外】
出场：人物

△ 可拍摄动作。

人物：台词
```

正式交付不使用代码块、表格、引用块或卡片。用户要求完整剧本时，展示全部分集和全部结局；内部滚动批次不改变交付范围。

## 验收标准

### 画布与缓存

- Canvas 项目定位唯一，流程结构、公开逐集目录、汇总稿和缓存文件已创建。
- 每个拓扑节点都有一个对应的公开逐集文件和隐藏分集缓存。
- 公开层不包含隐藏分析、情绪数值、生产卡和校验记录。
- 缓存中的全局事实、拓扑、人物、物件、钩子和分集文件完整。
- 汇总稿与公开逐集文件一致，不是重新生成的另一套正文。

### 结构

- 第一集是唯一入口，全部节点可达，无循环、孤立和断头。
- 流程图、选项、生产卡和下游参数来自同一拓扑。
- 选择分级正确，重大路线具有足够差异节点。
- 情绪有压制、释放、反噬、翻盘或明确题材例外，结局落点不同。

### 逐集与执行组

- 执行组按拓扑中的完整戏剧单元划分，不按固定集数划分。
- 互动节点与全部即时结果同组，最终选择与全部直接结局同组；汇合组读取全部来路。
- 每组开始前已估算容量，并为双校验和自动修复保留余量。
- 每集执行冻结生产卡，前后状态连续。
- 每集中文对白校验和连续性校验均通过，组级互动、分支和情绪校验通过。
- 规则、证据、物件来源和代价通过动作或台词让观众看懂。
- 钩子有后续回答，人物与道具状态已回写缓存。

### 全剧

- 人物知情、关系、弧光和权力变化无冲突。
- 道具与证据来源、持有、状态和回收完整。
- 情绪脊在实际剧本中兑现，不是线索平推。
- 下游参数与剧本事实一致。
- 用户完整稿包含全部节点和结局。

## 失败处理

- Canvas 存在多个候选：按标题 slug、任务关联和最近更新时间自动选择，并把选择依据写入缓存。
- Canvas 不存在：在当前 workspace 的 `canvas/` 下创建以游戏标题 slug 命名的项目。
- 缓存父目录不存在：使用 `exec` 创建后再写文件。
- 上游事实存在冲突：按用户明确内容优先、正式字段优先、具体描述优先于概括描述的顺序统一；仍有多种解释时采用对核心目标和既有资产改动最小的一种，并把假设写入隐藏缓存，不中断流程。
- 结构或情绪失败：返回全局规划和受影响生产卡。
- 中文对白失败：只改失败场次，复检后再冻结。
- 连续性失败：修正当前集或前置真实结尾，更新依赖节点。
- 全剧校验发现冲突：按依赖范围定点修复，不整部重新生成。
- 工具或画布暂时不可用：不得声称已写入画布；改为输出可恢复的缓存文件并说明实际状态。

## 边界

- 不把缓存内容展示给用户或写入公开页面。
- 不让子任务直接修改画布和缓存。
- 不用 `todo` 替代剧情缓存。
- 不在第二阶段重新设计已冻结的全局结构；确需改变时返回第一阶段并更新所有受影响状态。
- 不复制素人剧本或金标的人物、台词和情节，只学习自然来回、信息递进和权力变化。
