# Skill 编写规范

> 本规范用于本仓库所有现有与未来 Skill 的编写、重构和验收。
>
> 核心定位：**SKILL.md 是供模型稳定执行的产品规范，不是开发日志、问题复盘或提示词补丁集合。**

---

## 一、基本原则

### 1. 只写产品规范

SKILL.md 只说明：这个 Skill 做什么、读取什么、传递什么、按什么流程执行、怎样算合格、失败后怎么修复。

禁止写入测试病史、情绪化警告、补丁过程和已废弃机制。历史结论写进项目文档，不写进活动 Skill。

### 2. 名称唯一

- 后台名、目录名、调用名统一使用全小写连字符，例如 `episode-generator`。
- 中文展示名在界面、标题和正文中一致。
- 同一字段和内部概念只使用一个正式名称，不同时维护多套中英文同义词。
- `ID` 等已确认字段组成部分可以保留。

### 3. 正式字段与内部信息分开

- 正式字段是上下游真实接收和传递的信息，名称固定。
- 内部信息由当前 Skill 自行推导，用于规划和验收，不要求上游提供，也不向用户展示。
- 内部信息如需传给下游，必须包裹在已经定义的正式字段中，或等工程正式确认后再增加接口。

### 4. 用户呈现与下游传参分开

- 用户呈现是创作者直接看到的内容。
- 下游产物是模块间继续传递的数据。
- 下游字段不能决定用户回复形式。
- 用户未明确要求原始数据时，不展示内部对象、程序字段、分析字段、情绪数值或代码块。

### 5. 内容规则必须有优先级

当规则冲突时，低优先级不得破坏高优先级。例如分集剧本：

```text
观众看懂
> 场景有戏
> 人物说人话
> 制片格式正确
```

不能为了格式整齐牺牲流畅度，也不能为了台词漂亮让因果变得难懂。

---

## 二、SKILL.md 标准结构

无关章节可省略，已有章节按以下顺序组织：

```text
---
name
 description
---

# 中文角色名

## 主要职责
## 上游依赖
## 下游产物
## 输出格式
## 字段命名规则
## 主流程
## 内部分析（不展示给用户）
## 参考资料读取规则
## 交付前验收流程

## 其它专项规则
## 正式输出结构（如适用）
## 验收标准
## 失败处理
## 安全与生成边界
## 触发测试示例
## 不应触发的反例
```

专项规则根据能力需要增加，例如故事结构、资产引用、情绪推导、互动结构、剧本正文、台词写法、分镜语法和技术传参。

---

## 三、Frontmatter

### name

使用后台真实名称。目录名、`name` 和默认调用名完全一致：

```yaml
name: episode-generator
```

### description

一段话完成四件事：

1. 产物是什么；
2. 什么需求触发；
3. 具体负责什么；
4. 哪些任务不负责。

不在 description 中展开方法论、内部字段、工程结构和调试历史。

---

## 四、主要职责

先用一段自然语言定义能力，再分别列出：

```text
这个技能负责：
- ……

这个技能不负责：
- ……
```

正文职责必须与 description 一致，不能前后越界。

---

## 五、上游依赖

### 正式输入字段

每个输入字段说明：字段名、是否必填、数据形态、包含内容、缺失时动作。

示例：

```text
- 游戏企划：必填，对象。包含故事标题、一句话概述、故事核心目标、剧情描述、核心冲突、世界观、主题、故事体量和推荐结局数。
- 角色资产：必填，对象或对象列表。直接读取完整角色资产。
```

### 不用技术字段绑架上游

能够根据正式输入稳定推导的叙事引擎、实际节点总数、情绪数值、互动图和路径统计，应由当前 Skill 内部生成，不要求上游额外提供。

### 资产必须提供完整内容

- 输入完整角色、场景、道具资产，而不是无法展开的 ID 数组。
- 原资产已有 ID 或标识时原样沿用。
- 没有 ID 时使用资产名称或原资产唯一标识。
- 当前 Skill 不额外编造资产 ID。

### 门禁顺序

多上游能力必须写明先后。例如：

```text
大纲生成师 → 资产设计师 → 分集规划师
```

上游缺失时先补上游，不越权编造正式产物。

---

## 六、下游产物

### 只列真实业务字段

字段列表只写字段名，可见性和来源在正文说明。

推荐：

```text
- 分集ID
- 分集标题
- 分集剧本
- 剧本分析
```

不在字段名后追加括号解释。

### 根据下游需要传递信息

用自然语言说明：

```text
- 向分镜与故事板传递……
- 向互动程序传递……
- 不向分镜传递完整互动跳转过程……
```

只传对应下游真正需要的信息。

### 开放对象与固定对象

- 给模型理解的对象可开放，例如`剧本分析`，下游自行解析。
- 给程序执行的对象必须固定子字段，例如`互动节点`的选项和跳转。
- 工程命名未确定前使用唯一一套中文临时名称，不同时维护英文版本。

---

## 七、输出格式

本节只规定用户看到什么：

- 用户要结构时展示什么；
- 用户要完整内容时展示什么；
- 用户请求含糊时默认如何处理；
- 哪些内部字段禁止展示；
- 用户明确要求原始数据时如何处理。

内部分析、剧本分析、程序跳转和情绪数值不得自动出现在用户回复中。

钩子可记录在内部剧本分析中，但用户剧本必须通过最后动作、台词或事件自然体现，禁止额外写：

```text
钩子：……
```

---

## 八、字段命名规则

明确以下事项：

- 正式输入输出使用什么语言；
- 哪些缩写或 ID 保留；
- 旧字段如何兼容；
- 内部概念如何唯一命名；
- 工程命名未确定时如何维护临时字段。

原则：正式字段以真实上下游为准；内部概念用唯一中文名；旧英文参数只做兼容理解，不向用户展示，也不维护为第二套权威数据。

---

## 九、主流程

使用编号列表，每步只完成一个明确动作：

1. 判断用户请求；
2. 检查正式输入；
3. 补齐前置能力；
4. 读取字段；
5. 内部规划；
6. 生成内容；
7. 填入正式字段；
8. 执行验收；
9. 展示给用户并传给下游。

复杂方法与案例放专项规则和 references，不塞进主流程。

---

## 十、内部分析（不展示给用户）

内部分析记录工作状态与派生信息，不输出隐藏思考过程。

可记录：请求类型、门禁状态、体量、结局数、结构选择、节点规模、情绪脊、互动图、路径统计、内容分析、呈现模式和验收状态。

内部信息可整理进已定义下游字段，但仍不向用户展示。同一概念不得使用多个名称。

---

## 十一、References

### 标准结构

```text
读取时机 → 核心原则 → 分类规则 → 示例或真人语料 → 验收标准
```

### 文件名

统一使用小写英文连字符，例如：

```text
episode-writing-rules.md
chinese-dialogue-craft.md
scene-flow.md
```

### 主文件显式引用

SKILL.md 必须说明什么时候读取、学习什么、哪些内容不能机械复制。

### 真人金标

- 不使用模型自产内容作为金标。
- 优先使用真实制作剧本或真人公开语料。
- 保留连续场景学习信息顺序和对话节奏。
- 标注来源和使用边界。
- 学结构与说话方式，不复制人物、世界观和剧情。

### 分题材语料

台词指南应覆盖历史古装、城市职场、农村市井、涉案谈判、青春校园、亲密关系等常用题材。每类说明“学什么、不学什么”，避免连同陈旧表达和不安全内容一起照搬。

---

## 十二、交付前验收

验收必须能够核对，不能只问“是否完成”。

### 工程验收

检查正式字段、节点数、跳转、循环、孤立、断头、资产引用和结局数量。

### 内容验收

按优先级检查。上一层不过，先返工：

```text
一、观众看懂
二、场景有戏
三、人物说人话
四、制片格式正确
```

### 用户呈现验收

确认用户没有看到内部分析、技术字段、未要求的结构化数据、`钩子：`或`剧本分析：`等解释性标记，并确认请求结构时给结构、请求完整内容时给完整内容。

---

## 十三、失败处理

使用“问题 → 明确动作”：

- 大纲缺失 → 调用大纲生成师；
- 资产内容缺失 → 调用资产设计师；
- 剧本像梗概 → 补目标、阻力、交锋、信息差与状态变化；
- 人物凭空出现 → 补出场动作、身份锚和来意；
- 用户看到内部分析 → 保留内部数据，重整用户呈现；
- 钩子被直接解释 → 删除说明，把内容写成本集最后事件。

失败处理只指出回到哪一节修复，不复制规则全文。

---

## 十四、维护与提交

### 权威源

Git 仓活动 Skill 目录是唯一权威源；对外文稿每次提交后覆盖同步；历史备份加入忽略规则，不作为活动 Skill 上传。

### 修改流程

1. 修改权威源；
2. 全仓搜索旧名称和旧字段；
3. 检查主文件与 references 引用；
4. 检查默认调用配置；
5. 同步对外文稿；
6. 提交推送；
7. 更新 README 与权威认定文档。

提交信息应说明改动原因、正式字段变化、上下游影响和文稿同步状态。
