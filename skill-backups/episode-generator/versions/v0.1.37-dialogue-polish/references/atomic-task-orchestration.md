# 原子任务编排协议

## 1. 目的

本协议把“模型愿意执行”改为“控制器只允许执行当前一步”。阶段封印负责内容来源与失效传播；原子任务账本负责实际调度。两者缺一不可。

## 2. 两个不可混淆的对象

- **分集节点**：观众一次连续观看的戏剧单位，也是流程图唯一节点，用 `episode-NNN` 标识。选择、反馈、汇合和结局节点都各是一集。
- **模型任务**：一次调用只完成一个语义动作，例如写一张生产卡、写一集初稿、审一集对白或定点修一集。

上游要求“18—22 个剧情节点”时，就是 18—22 集。禁止新增节点到分集的映射层，禁止把多个流程节点折叠成一集。

## 3. 唯一合法的调度单元

控制器维护私有 `atomic-tasks.json`。每项任务至少包含：

- `id`、`kind`、`scope_id`、`role`
- `dependencies`
- `allowed_inputs`、`allowed_outputs`
- `input_digest`、`output_digest`
- `status`、`attempt`、`issues`

状态只能是 `pending`、`running`、`complete`、`needs_fix`、`blocked`。任一时刻最多一个 `running`。只能领取依赖均为 `complete` 的第一项任务。

一次模型调用只能对应一项账本任务。调用前先落盘 `running`；调用后先落盘产物和摘要，再由控制器更新状态。中断后继续时，优先恢复同一 `running` 任务；不得跳到后续任务。

## 4. 作者、审稿人与控制器分权

- 作者只产出候选内容，不得声明通过。
- 审稿人只返回覆盖清单与具体问题，不得改正文。
- 修订者只修复已登记问题，不得顺手重写其他内容。
- 控制器根据结构化审查结果计算是否通过；模型写出的 `PASS`、`通过`、自评分均不具有状态效力。

审查结果只有同时满足以下条件才由控制器判定为通过：指定检查项全部覆盖；`issues` 为空；审查绑定当前产物指纹。缺字段、漏覆盖或指纹不一致都视为未完成，不是通过。

## 5. 全链顺序

规划链：

1. 上游转译
2. 情绪脊写作
3. 情绪脊独立审查
4. 因果图写作
5. 因果图独立审查
6. 分集拓扑写作
7. 路径独立审查

生产链按分集滚动：

1. 当前分集轻量执行卡
2. 当前分集初稿
3. 当前分集整场人话润色
4. 保存当前分集事实与正文指纹

当前分集完成后，下一集才可领取写作任务。全部分集完成后才可进行全剧事实连续性检查和最终公开组装。

## 6. 失败与失效

审查发现问题时，控制器生成或开启归属明确的修复任务，把原审查记为 `needs_fix`，并阻断所有下游。修复改变产物指纹后，旧审查自动失效，必须对新指纹重审。

上游产物改变时，所有直接或间接依赖它的任务恢复为 `pending`，清空旧输出指纹；不得靠文字说明保留旧通过状态。

## 7. 公开边界

账本、情绪坐标、因果图、审查记录、问题单、状态记忆和各类缓存均为私有。用户若要求进度，只展示中性过程状态，例如“正在生成分集流程图”“第 4/18 集正在写作”“第 7 集有逻辑问题，正在定点修复”。最终只公开：各集梗概、分集流程图、完整剧本。
